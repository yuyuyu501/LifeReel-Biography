# ADR 0004：实时采访编排与渐进式服务拆分

- 状态：Accepted
- 日期：2026-09-07
- 关联：ADR 0001（部分演进，不废弃其独立 Worker 决策）

> 章节审核与锁定部分已由 ADR 0006 取代；其余编排和服务边界决策继续有效。

## 背景

采访现在需要在每次文字、语音或素材输入后完成证据分析、记忆编译、信息缺口判断、追问生成和章节剧本更新。继续由前端依次调用多个领域接口会产生部分成功、重复调用和状态不可见问题。直接切换到数据库独占微服务则会在当前阶段引入不必要的分布式事务和运维成本。

## 决策

新增 Interview Orchestrator 作为工作流所有者，以持久化工作流和 Redis 任务驱动处理。Evidence、Memory、Script 保持明确的服务函数和表所有权，Worker 只调用内部执行接口。

部署采用渐进式方案：第一阶段仍由同一 FastAPI 进程承载 Core API 和领域服务，并共享 PostgreSQL 实例；模块之间通过结构化 `ScriptUpdateBrief` 和工作流状态交互。第二阶段再提供独立进程入口和 transactional outbox；第三阶段按真实容量与团队边界拆分数据库。

剧本更新以章节为最小单位，并采用“一章一份当前稿件”的覆盖式更新模型。每轮采访都用该章全部有效记忆重新整理连续正文，而不是追加新场景或新草稿；当前稿允许随采访持续更新。

采访与剧本共享章节画像。每个系统章节定义关键词、必问主题、越界主题、采访目标和写作目标；已知记忆与冲突均按当前章节过滤。这样所选章节同时约束下一问、缺口判断和剧本内容。

## 后果

- 用户可以在采访过程中看到可追溯的实时章节草稿和针对性追问。
- 数据库唯一约束保证同一项目和章节不会再次产生多份稿件。
- 每次 Turn 有持久状态、幂等键、失败码和可重试路径。
- 当前仍存在共享数据库耦合，但边界被显式记录，不能跨服务随意写表。
- Redis 入队与数据库事务之间暂有短窗口，阶段 B 必须以 outbox 消除。
- SSE/WebSocket 不是必要依赖，客户端先通过短轮询读取工作台。
