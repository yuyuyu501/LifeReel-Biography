# 支付宝电脑网站支付

## 订单与到账

Web 钱包的自动支付模式使用 `alipay.trade.page.pay`，产品码为
`FAST_INSTANT_TRADE_PAY`。确认支付先持久保存所属账号、金额、请求幂等键、
结算来源及 APPID，再打开支付宝官方收银台。二维码由支付宝收银台提供，
不再把静态收款码当作自动支付入口。单笔仍限制为 0.01–200 元。

支付宝异步通知入口为 `POST /v1/wallet/alipay/notify`。该精确路径允许支付宝
无需用户登录访问，但必须使用支付宝公钥通过 RSA2 验签，并匹配订单来源、
APPID、商户订单号、金额和真实交易号。仅 `TRADE_SUCCESS` 或
`TRADE_FINISHED` 入账；配置了卖家 UID 时额外校验 `seller_id`。
当前为商户自营应用直连模式，不使用第三方应用授权 token。

钱包和订单行按固定顺序加锁，订单状态、充值账本与余额在同一事务中提交；
交易号全局唯一，同一订单的重复通知不重复入账。付款人声明、浏览器返回参数、
打开收银台及创建订单均不能增加余额。

订单查询及账务服务后台循环调用 `alipay.trade.query` 补偿漏通知，并验证响应
原始 JSON 对象的 RSA2 签名。每单查询间隔至少 15 秒，后台每轮最多查 5 单，
覆盖近两天待付款订单。请求失败保留待付款状态，支付宝明确关闭后才关闭订单。
Web 同标签页刷新后恢复订单查询；即使用户关闭页面，通知和后台查单仍运行。

历史订单迁移为 `manual_review`，继续保留人工核实路径；API 自动支付订单不能
调用人工核实、付款声明或本地取消接口，避免绕过支付宝真实状态。
数据库迁移为 `20261118_0049`，存在自动支付订单时拒绝降级丢弃结算来源。

## 私有配置

仅在私有环境中配置，不把密钥内容或收款资料提交 Git：

```dotenv
ALIPAY_ENABLED=true
ALIPAY_APP_ID=<已开通电脑网站支付的应用ID>
ALIPAY_PRIVATE_KEY_PATH=/data/alipay/application-private.pem
ALIPAY_PUBLIC_KEY_PATH=/data/alipay/alipay-public.pem
ALIPAY_SELLER_ID=
ALIPAY_NOTIFY_URL=https://bianjiaigc.com/v1/wallet/alipay/notify
ALIPAY_RETURN_URL=https://bianjiaigc.com/wallet
```

支持密钥工具生成的 Base64 DER 和 PEM。支付宝公钥与应用公钥用途不同，
私钥用于下单签名，支付宝公钥用于通知及查询响应验签。
密钥存放于宿主机 `data/alipay/`，仅只读挂载给 billing 服务；目录权限 700，
私钥权限 600。不要写入前端构建、日志、镜像或公开静态目录。
自动模式开启但密钥不完整时关闭新付款，不悄悄切回静态收款码。
关闭新付款开关后，已有支付仍可通过有效签名通知核实入账。

`ALIPAY_SELLER_ID` 可填写商户支付宝 UID（2088 开头），不是登录手机号。
该项是应用与订单校验之外的额外约束，通知必须匹配该 UID；主动查询由本应用
签名发起并验签返回结果，不要求查询返回可选的卖家字段，但返回时也会核对。
更换 APPID 或支付宝公钥前应处理旧应用未结订单，不能将旧订单改为新应用。

## 发布与验收

先完成本地模拟测试及独立 PostgreSQL 的迁移、并发入账验证，再按部署流程
备份数据库、环境及回退镜像，推送精确提交，构建、迁移、重建容器并验证健康。
密钥另行私有传输，首次替换前保留原文件。回退代码时保留新增账务数据和迁移；
已有自动支付订单不能用旧数据库覆盖。

常规测试只使用合成密钥、合成通知与模拟查询，不创建真实支付宝交易。
上线后由经营者在真实支付宝收银台核对收款主体，完成一笔 0.01 元付款，
核对账号余额、唯一账本记录及支付宝交易号。这一步才验证商户签约权限、
后台登记密钥与实际付款到账的完整链路。

微信、抖音小程序的原生支付仍未开启。本次电脑网站支付不能替代小程序平台收银台。
